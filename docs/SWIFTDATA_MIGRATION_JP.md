# SwiftData 移行 設計書（案）

クリップボード履歴とスニペットの保存先を Realm から SwiftData へ移す計画です。
**合意を取ってから実装に入る**ための文書で、決めていただきたい点は最後の「8. 決めていただきたいこと」にまとめています。
実装が終わったら、確定した内容を [DESIGN_JP.md](DESIGN_JP.md) / [DESIGN.md](DESIGN.md) へ移し、この文書は削除します。

- 対象バージョン: v1.5.0（ブランチ `feature/swiftdata-migration`）
- 前提: macOS 15.0 以降・Apple Silicon 専用（v1.4.0 で確定）

---

## 1. 対象と現状

SwiftData へ移すのは、いま Realm に入っているものだけです。**セキュア情報（パスワード・TOTP など）はキーチェーンにあり、この移行の対象外です。**

| 保存先 | 中身 | 保護 | この移行で |
|---|---|---|---|
| キーチェーン `…Thoth.SecureMenu` / `user-data` | セキュアアイテム・指紋パスワード | キーチェーン | **触らない** |
| キーチェーン `…Thoth.Database` / `app-keys` | Realm と `.data` の暗号鍵 | キーチェーン | **形式を変えない**（読むだけ） |
| `~/Library/Application Support/io.github.boyaki-machine.Thoth/default.realm` | 履歴の一覧情報（本文の先頭 1 万文字・種別・日時・内容ハッシュ）、スニペット・フォルダ（本文を含む） | Realm の暗号化（AES-256） | **SwiftData へ移す** |
| `~/Library/Application Support/Thoth/*.data` | クリップの実データ | AES-256-GCM | そのまま使う |
| `~/Library/Caches/com.pinterest.PINDiskCache.PINCacheShared/` | 画像クリップのサムネイル | **暗号化なし** | 暗号化して DB へ入れ、キャッシュは消す |

調査で分かった前提:

- Realm を使っているのは 14 ファイル・約 95 行。クエリは「日時順・番号順に並べる」「日時で絞る」「主キーで引く」だけで、複雑なものはない
- 変更通知は 2 箇所（メニューの再構築用）だけ
- 履歴パネル・全文検索はすでに値型のスナップショット（`ClipItem` / `ClipRef`）を介して動いている
- 履歴の検索はメモリ上で行っている（DB のクエリは使っていない）ので、項目を暗号化しても検索は変わらない
- 履歴の上限は既定 30 件。すべての項目を起動時に復号しても負荷は無視できる
- **サムネイルは実は縮小されていない。** `resizeImage` は元画像の表現に表示サイズを付けるだけなので、キャッシュには元の解像度の画像が入る（手元の実例では 1 件 30MB）。スクリーンショットの全体が平文で `~/Library/Caches` に残っている

SwiftData の挙動は、小さな試作（macOS 27 / Xcode 27、デプロイターゲット 15）で次を確認しました。

| 確認したこと | 結果 | 設計への影響 |
|---|---|---|
| 一意属性の値が同じモデルを挿入する | 既存のものが置き換わる（upsert） | 「同じ内容を上書き」をそのまま表現できる |
| 関連（フォルダ → スニペット）の並び順 | **保たれない**（`[3, 0, 4, 1, 2]`） | 既存の `index` 属性で必ず並べ直す |
| 並べ替え付き取得・関連をまたぐ条件指定 | 期待どおり | 問題なし |
| 保存後の通知 `ModelContext.didSave` | 届く | 変更通知の代わりに使える |
| フォルダ削除で中のスニペットも消えるか（`.cascade`） | 消える | Realm で手書きしていた削除をまとめられる |
| 保存ファイル | `.store` / `-wal` / `-shm` の 3 つ | 移行・退避はこの 3 つを 1 組で扱う |

## 2. 要件

| # | 要件 | 理由 |
|---|---|---|
| R1 | **保存時の暗号化を今より弱めない。** 本文・スニペット・フォルダ名・サムネイル・内容ハッシュを平文でディスクに置かない | SwiftData（中身は SQLite）には暗号化の機能が無い。そのまま移すとコピーしたパスワードなどが平文で残る |
| R2 | **データを失わない。** とくにスニペットは本人が作ったもので作り直しが効かない。移行に失敗しても元のデータは無傷で残す | セキュア情報と同じく「バージョンアップでデータを失わせない」方針 |
| R3 | **旧バージョン（v1.4.x）に戻しても壊れない。** 移行後も Realm のファイルには触らない | 不具合時の退避経路 |
| R4 | **キーチェーンの保存形式を変えない。** 新しいエントリも作らない | 鍵まわりは消失事故の原因になりやすく、既存の防御（読めないときは作らない等）を崩したくない |
| R5 | メニュー・パネルの表示が今より遅くならない | 常駐アプリの体感に直結する |

## 3. 方式

### 3-1. 構成：保存層を 1 枚挟む

UI やサービスが Realm のオブジェクトを直接触っている今の形をやめ、**値型だけをやり取りする保存層**を挟みます。暗号化・復号はこの層の中だけで行い、外には平文の値型しか出しません。

```
 MenuManager / PasteService / HotKeyService / 履歴パネル / スニペット編集 …
                 │ 値型（ClipRecord / SnippetFolderRecord / SnippetRecord）
                 ▼
     ClipHistoryStore / SnippetStore（プロトコル）
          ├─ RealmClipHistoryStore … 移行元・失敗時の退避先（v1.5.x のみ残す）
          └─ SwiftDataClipHistoryStore … 本番
                 │ 暗号化した項目（FieldCipher）
                 ▼
        SwiftData（Thoth.store / -wal / -shm）
```

- 最初に **Realm のまま**保存層を入れて、挙動が変わらないことをテストで固めます（手順 S1）。そのあと同じテストを SwiftData 版でも通します
- 変更通知は、保存層が保存のたびに通知（`.thothStoreDidChange`）を出す形に一本化します。今の Realm の変更通知 2 箇所はこれに置き換えます
- **スレッド**: SwiftData の `ModelContext` はスレッドをまたげないので、保存層が専用の直列キューで 1 つだけ持ちます（今の `saveQueue` と同じ考え方）。UI は保存層が保存のたびに更新する復号済みのスナップショットを読むので、メインスレッドで DB を待ちません（R5）

### 3-2. スキーマ（v1）

平文で置くのは「並べる・引く・構造を保つ」ために必要な列だけです。表示に使う中身は項目ごとにまとめて 1 つの暗号化された塊（`sealedPayload`）にします。塊の中は JSON で、`version` を持たせます。中身の項目が増えても SwiftData のスキーマ移行が要らなくなります。

| モデル | 平文の列 | 暗号化する中身（`sealedPayload`） |
|---|---|---|
| `StoredClip` | `id`（内容キー、後述）・`updateTime`・`dataPath`（UUID のファイル名） | タイトル（本文の先頭 1 万文字）・種別・カラーコードか否か |
| `StoredClip` のサムネイル | ― | `sealedThumbnail`（縮小した PNG を暗号化。`@Attribute(.externalStorage)`） |
| `StoredFolder` | `id`（UUID）・`index`・`enable` | フォルダ名 |
| `StoredSnippet` | `id`（UUID）・`index`・`enable`・`folder`（関連） | タイトル・本文 |
| `StoreMeta` | 移行の記録（移行日時・移行元の件数・スキーマ版） | ― |

- `VersionedSchema` / `SchemaMigrationPlan` を最初から使い、将来のスキーマ変更に備えます
- スニペット・フォルダの識別子は Realm の `identifier`（UUID）をそのまま引き継ぎます。フォルダのホットキーはこの値で紐づいているため、変えるとホットキーが外れます

### 3-3. 項目の暗号化（`FieldCipher`）

- 方式: AES-256-GCM（CryptoKit）。形式は `.data` ファイルと揃えて `"TSF"(3B) + 形式版 0x01(1B) + nonce(12B) + 暗号文 + タグ(16B)`
- **付加データ（AAD）に「モデル名・id・項目名・形式版」を入れます。** 暗号文を別の行や別の項目へ差し替えられても、復号に失敗して気づけます（今の `.data` には無い防御）
- **鍵はキーチェーンに新しく作らず、既存の `.data` 用の鍵から HKDF-SHA256 で導出します**（R4）。用途ごとに `info` を変えて 2 本作ります
  - 暗号化用: `info = "io.github.boyaki-machine.Thoth.store.seal.v1"`
  - 内容キー用: `info = "io.github.boyaki-machine.Thoth.store.content-key.v1"`

### 3-4. 内容ハッシュは鍵付きハッシュにする

今の主キー `dataHash` は内容から決まるハッシュ（文字列なら CFString のハッシュ）です。暗号化された Realm の中にある今は問題ありませんが、SwiftData で検索用に平文の列として置くと、**短いパスワードなどを総当たりして一致を確かめる手掛かり**になります。

そこで、保存する主キーは `id = HMAC-SHA256(内容キー用の鍵, dataHash)` の 16 進表記にします。

- 「同じ内容を上書き」の判定は、同じ内容なら同じ `id` になるので upsert でそのまま実現できます
- 「上書きしない」設定のときに乱数を使っている今の動作もそのまま引き継げます
- アプリ内（メニューの `representedObject`、`PasteService`、履歴パネル、全文検索）で使う識別子も、この `id` に揃えます

### 3-5. サムネイル

- **本当に縮小した画像を作ります。** 表示サイズ（既定 100×32pt）の 2 倍のピクセルに描き直し、PNG にします。数 KB になる見込みです
- 暗号化して `StoredClip.sealedThumbnail` に入れます。クリップを消せばサムネイルも一緒に消えるので、孤立したキャッシュが残りません
- 表示時はメモリ上のキャッシュ（`NSCache`）だけを使います
- PINCache は廃止します。移行時にはキャッシュの画像は読まずに（安全でないアンアーカイブを避けるため）、`.data` から作り直します。そのうえで `~/Library/Caches/com.pinterest.PINDiskCache.PINCacheShared/` を削除します

### 3-6. 鍵が使えないとき

鍵が使えない状況は 2 通りあります。

1. 再署名に失敗して、まだ鍵を作れない
2. 鍵はあるのにキーチェーンから読めない

今は 1 のとき平文で保存し、2 のときは「終了 / 履歴・スニペットをリセット」を選ばせています。

**案 A（推奨）: その起動中はメモリ上だけで動き、ディスクには書かない。**

- 起動時に一度だけ「暗号鍵が使えないため、この起動中の変更は保存されません」と知らせます
- スニペット編集ウィンドウにも同じ注意を出します
- 平文をディスクに置く経路が無くなり、「リセット」でデータを消す選択肢も要らなくなります

案 B: 今と同じく平文で保存し、鍵が使えるようになったら暗号化し直す。

- 機能は保てますが、平文と暗号文が混ざる状態を扱うコードとテストが増えます

移行が済むまでの間（v1.5.x で移行前の状態）は、どちらの案でも**今の Realm のまま動かします**。鍵がなければ移行できないためです。

## 4. 移行の手順（Realm → SwiftData）

起動時、鍵が使えて Realm の準備が終わったあとに、`StoreMeta` に移行の記録が無ければ実行します。

1. Realm を**読み取り専用**で開き（`readOnly: true`、同じ鍵）、全件を値型に読み出す
2. **一時ファイル**（`Thoth.migrating-<UUID>.store`）に新しいストアを作って書き込み、保存する
3. 一時ストアを開き直して**照合する**
   - 件数（履歴・フォルダ・スニペット）
   - 1 件ずつ、復号した全項目が読み出した値と一致すること
   - フォルダ・スニペットの並び順（`index` 順）
   - `.data` ファイルの参照先が存在すること（無ければ記録だけ残して先へ進む。今も同じ状態のため）
4. 照合に通ったら、一時ストアの 3 ファイルを本番の名前（`Thoth.store` ほか）へ移し、`StoreMeta` に移行日時と件数を書く
5. サムネイルを `.data` から作り直し、PINCache のフォルダを削除する（失敗しても次回起動時にやり直す）

失敗したとき（どの段階でも）:

- 一時ファイルを消し、**この起動は Realm のまま動かします**（保存層の Realm 版を使う）。次回起動時にやり直します
- Realm のファイルには最初から最後まで書き込みません（読み取り専用で開くため）

旧バージョンに戻したとき（R3）:

- v1.4.x は Realm のファイルを開くので、**移行した時点の履歴・スニペット**が見えます
- 移行後に v1.5.0 で行った変更（新しい履歴、スニペットの編集）は旧版には見えません。旧版で行った変更も、v1.5.0 に戻したときには反映されません（既知の制限として DESIGN に書きます）

後片付けは v1.6.0 以降で行います。Realm の依存を外す版で、`default.realm` 一式と `default.v20.backup.realm`（2026-07-20 に Realm が作った古い形式のバックアップ）を削除します。削除の前に、移行済みであること（`StoreMeta`）を必ず確かめます。

## 5. 実装の手順（ブランチ内のコミット単位）

| 手順 | 内容 | 主なテスト |
|---|---|---|
| S1 | 保存層（プロトコルと値型）を入れ、既存コードを **Realm 版の保存層経由**に置き換える（挙動は変えない） | 保存層の契約テスト（追加・上書き・上限超過の削除・並べ替え・フォルダ間の移動・連鎖削除・変更通知） |
| S2 | `FieldCipher` と、HKDF・HMAC による鍵の導出 | 往復、改ざんの検出、AAD 違い（行・項目の差し替え）の検出、**固定の暗号文による形式の固定** |
| S3 | SwiftData 版の保存層 | S1 の契約テストを**両方の実装で**通す。DB ファイルに平文の目印が現れないことを確かめるテスト |
| S4 | 移行処理 | テスト中に作った Realm と、**リポジトリに置く固定の Realm ファイル**（テスト用の鍵で暗号化）の両方から移行する。照合に失敗したら切り替えないこと、Realm のファイルが一切変わらないこと（前後のハッシュ比較）、途中で落ちても再実行で正しく終わること |
| S5 | サムネイルの縮小・暗号化保存と PINCache の廃止 | 縮小後の画素数、往復、クリップ削除でサムネイルも消えること |
| S6 | 鍵が使えないときの扱い（案 A または B）、DESIGN（日英）への反映、v1.5.0 | 鍵なしのときにディスクへ平文を書かないこと（案 A の場合） |

どの手順も、これまでと同じく「実装を意図的に戻すと落ちる」ことを確かめてから積みます。

移行の固定テストに入れる境界値:

- 空のタイトル・ちょうど 1 万文字のタイトル
- 結合絵文字・CRLF・全角文字
- 番号に抜けがあるスニペット、無効にしたフォルダ・スニペット
- カラーコードのクリップ、画像クリップ、ファイル名のクリップ
- 「上書きしない」設定で入った同じ内容の履歴 2 件

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| SwiftData の不具合（macOS 14〜15 では、バックグラウンドのコンテキストや関連まわりの不安定さが報告されている） | コンテキストを 1 つの直列キューに閉じ込める。スキーマは継承・CloudKit なしの単純な形にする。保存は明示的に行う。契約テストで Realm 版と挙動を揃える |
| 移行の不具合でデータが欠ける | 一時ストアで照合してから切り替える。Realm は読み取り専用で開く。固定フィクスチャで回帰を防ぐ |
| ストアが壊れて開けない | 削除せず `Thoth.store.broken-<日時>` へ退避する。Realm が残っていれば再移行を提案し、無ければ空のストアで起動する（「リセット」でデータを消す選択肢は設けない） |
| 復号の負荷でメニューが遅くなる | 復号は保存時・起動時にまとめて行い、UI は復号済みのスナップショットを読む。履歴の上限は既定 30 件 |
| WAL などに平文が残る | 平文の列は識別子・日時・番号・有効フラグだけにする。S3 で、DB ファイル一式に目印の文字列が現れないことをテストする |

---

## 7. この移行でやらないこと

- `.data` ファイルの形式変更（AAD の追加など）。今の形式のまま読み書きします
- CocoaPods から SPM への移行（段階 4 で扱います）。ただし Realm は v1.6.0 で外すので、SPM へ移すものは 1 つ減ります
- 履歴・スニペットのエクスポート形式（スニペットの XML）の変更

| # | 事項 | 推奨 |
|---|---|---|
| D1 | 鍵が使えないとき（3-6） | **案 A**：その起動中はメモリ上だけで動き、ディスクへ平文を書かない |
| D2 | 内容ハッシュを鍵付きハッシュ（HMAC）にする（3-4） | **する** |
| D3 | 暗号化の鍵をキーチェーンに新しく作らず、`.data` の鍵から導出する（3-3） | **導出する** |
| D4 | サムネイルを本当に縮小して暗号化保存し、PINCache と平文キャッシュを消す（3-5） | **する**（旧版に戻すと、既存の履歴のサムネイルが出なくなる） |

| D6 | 旧版に戻して使った間の変更は、再度上げても取り込まない（4 章）。既知の制限として書くだけにする | **書くだけにする**（取り込み直す仕組みは、Realm のファイルの変更を確実に検出する方法が無く、誤って新しい変更を上書きしうる） |
