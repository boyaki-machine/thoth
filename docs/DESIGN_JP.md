## 1. Export / Import されるファイルのスキーマ

セキュア情報確認ウィンドウの Export（⚙ メニュー）で書き出される JSON は、**ユーザー自身が設定した機微情報**（`SecureUserData`）です。Import はこのファイルを読み込みます。アプリが自動生成する環境固有の情報（暗号鍵など）は Export に含まれません（[4. 情報の分類](#4-情報の分類ユーザー設定情報--アプリ生成情報) を参照）。

> **注意:** Export ファイルは平文の JSON です。取り扱いに注意してください。

### `SecureUserData`（Export/Import のルート）

| キー | 型 | 説明 |
|---|---|---|
| `version` | Int | スキーマバージョン（現行 `2`） |
| `items` | `SecureMenuItem[]` | セキュアアイテムの配列 |
| `cryptoPassword` | String?（省略可） | ファイル暗号化の固定パスワード（指紋パスワード）。未登録なら省略 |

### `SecureMenuItem`

| キー | 型 | 説明 |
|---|---|---|
| `itemID` | String | アイテムの安定 ID（UUID） |
| `title` | String | 表示名（例: "GitHub"） |
| `fields` | `Field[]` | フィールドの配列 |
| `displayOrder` | Int | メニューでの表示順 |

### `SecureMenuItem.Field`

| キー | 型 | 説明 |
|---|---|---|
| `fieldID` | String | フィールドの安定 ID（UUID）。ラベル変更後も履歴を追従させるために使用 |
| `label` | String | フィールド名（例: "Password"） |
| `value` | String | 値。TOTP の場合は otpauth URI / Base32 secret |
| `isPassword` | Bool | 値をマスク表示するか |
| `kind` | String | `"plain"` または `"totp"`（後述の後方互換のため、この 2 値しか書き込まれません） |
| `contentKind` | String（省略可） | 拡張種別 `"url"` / `"note"`。v1.2.0 で追加。通常の種別では出力されません |
| `history` | `FieldHistoryEntry[]` | 値の変更履歴（`plain` / `url` のみ記録。`totp` / `note` は残しません） |
| `createdAt` | Date | 作成日時 |

#### フィールド種別

| 種別 | JSON 表現 | 用途 |
|---|---|---|
| `plain` | `kind: "plain"` | ID・パスワードなど通常のテキスト |
| `totp` | `kind: "totp"` | `value` に otpauth URI / Base32 secret を保持し、選択時にワンタイムコードを生成 |
| `url` | `kind: "plain"` + `contentKind: "url"` | ログイン先などの URL。ブラウザで開ける |
| `note` | `kind: "plain"` + `contentKind: "note"` | 契約番号・連絡先などの複数行メモ |

### `FieldHistoryEntry`

| キー | 型 | 説明 |
|---|---|---|
| `value` | String | 過去の値 |
| `replacedAt` | Date | 置き換えられた日時 |

### 後方互換

- デコードは寛容に行われ、欠けているキーはデフォルト値で補完されます（`version` 欠落時は現行版、`kind` 欠落時は `plain`、`history` 欠落時は空、など）。
- **未知の種別は `plain` にフォールバックします。** 将来のバージョンが書いた種別を古いバイナリが読んでも、デコード自体は成功し値は保持されます。
- Import は現行形式（`SecureUserData` オブジェクト）を優先し、**旧形式（`SecureMenuItem` の配列のみ）の JSON もフォールバックで読み込めます**。過去バージョンで書き出したファイルもそのまま取り込めます。

### 前方互換（バージョンを戻した場合）

拡張種別（`url` / `note`）を `kind` キーに直接書くと、v1.1.x 以前は `kind` を enum として厳密にデコードするため **例外が発生し、セキュアアイテム全体が読めなくなります**。読めないデータの上に保存すると全件が失われるため、拡張種別は新しいキー `contentKind` に分離しています。

- 旧バージョンは `contentKind` を未知のキーとして無視し、`kind: "plain"` として読みます。
- **値は失われません。** TOTP secret も `kind: "totp"` のまま維持されます。
- ただし旧バージョンで保存し直すと `contentKind` が失われ、URL / メモは通常のテキストに降格します（値は残ります）。またメモを旧バージョンの単一行フィールドで編集すると改行が失われます。

### 読み出し不能時の保護

「Keychain の読み出しには成功したが内容を解釈できない」場合（データ破損など）、`SecureMenuService` は `errSecDecode` を返して読み出し不能として扱い、**すべての書き込みを拒否します**。空のデータで既存データを上書きしないための保護です。旧エントリからの移行も、旧データを解釈できない場合は移行を中止して旧エントリを残します。

## 2. 暗号化 / 復号に関する仕様

### 2-1. ファイル暗号化コンテナ（現行: バージョン 2）

**設計要件:** 「アプリが無い端末でも `openssl` コマンドだけで復号できること」。このため、暗号化本体を `openssl enc` の出力と完全互換にし、その外側に HMAC-SHA256 による認証（Encrypt-then-MAC）を付与しています。

**バイトレイアウト:**

| オフセット | サイズ | 内容 |
|---|---|---|
| 0 | 7 | マジック `"CLPYENC"`（ASCII） |
| 7 | 1 | バージョン `0x02` |
| 8 | 1 | フラグ（bit0: フォルダ由来 → 復号後に tar 展開） |
| 9 | 4 | PBKDF2 反復回数（UInt32 ビッグエンディアン、既定 200000） |
| 13 | 32 | HMAC-SHA256 タグ（先頭 13 バイト + 本体全体を認証） |
| 45 | 可変 | 本体 = `openssl enc` 完全互換:<br>`"Salted__"(8B) + salt(8B) + AES-256-CBC 暗号文（PKCS7 パディング）` |

**鍵導出:** PBKDF2-HMAC-SHA256 で **80 バイト**を一度に導出し、以下に分割します。

- 暗号鍵: 先頭 32 バイト
- IV: 続く 16 バイト
- HMAC 鍵: 続く 32 バイト

先頭 48 バイト（暗号鍵 + IV）は `openssl enc -pbkdf2` の鍵導出結果と一致します（PBKDF2 の出力はブロック単位で独立しており、長く導出しても前半は変わらないため）。これが openssl 互換の根拠です。

**認証:** ヘッダー（先頭 13 バイト）と本体全体を HMAC-SHA256 で認証します。アプリ内での復号は、この HMAC タグを**復号前に検証**することで改竄・誤パスワードを確実に検知します。openssl CLI での復号ではこの検証は行われません（誤パスワードの大半は CBC の PKCS7 パディングエラーで検出されます）。

**openssl での復号:**

```sh
# 先頭 45 バイトのヘッダーを取り除いてから openssl enc に渡す
tail -c +46 file.enc | openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -pass pass:PASSWORD -out restored
# フォルダ由来（オフセット 8 のフラグ bit0 が 1）の場合は tar -xf restored で展開
```

### 2-2. 復号のみ対応する過去形式

アプリの復号処理は、以下の過去形式も自動判別して読み込めます（暗号化時の出力は常に現行のバージョン 2）。

| 形式 | 判別 | 仕様 |
|---|---|---|
| バージョン 1 | `"CLPYENC" + 0x01` | AES-256-GCM 形式（旧実装、短期間のみ使用）。ヘッダー 29B + nonce 12B + 暗号文 + タグ 16B |
| レガシー | 先頭がマジックでない | `マーカー 8B + openssl enc 出力`。マーカーは `"CLIPYDIR"`（フォルダ）またはゼロ 8 バイト（ファイル）。鍵導出は PBKDF2-HMAC-SHA256 100000 回 |

`openssl enc -aes-256-cbc -pbkdf2` が出力した標準ファイル（マーカーなし）も、レガシー形式のファイル版として復号できます。

### 2-3. クリップボード履歴・スニペットの暗号化（保存時暗号化）

履歴とスニペットは SwiftData のストア（`Thoth.store`）に、クリップの実データは個別の `.data` ファイルに保存され、いずれも暗号化されます。これらはアプリ内部専用の鍵で暗号化され、**端末固有**です（Export 対象外・他端末とは互換しません）。

| 対象 | 方式 |
|---|---|
| ストア（SwiftData）の中身 | 項目ごとに AES-256-GCM。形式: `"TSF"(3B) + バージョン 0x01(1B) + nonce 12B + 暗号文 + タグ 16B`。付加データ（AAD）は `Thoth.store/v1\|<モデル名>\|<id>\|<項目名>` |
| クリップ `.data` ファイル | AES-256-GCM。形式: `"CLPYDAT"(7B) + バージョン 0x01(1B) + AES-GCM combined（nonce 12B + 暗号文 + タグ 16B）` |

SwiftData（中身は SQLite）には保存時暗号化の機能が無いため、表示に使う中身は項目ごとに暗号化した JSON（`sealedPayload`）にまとめます。平文のまま置くのは、並べる・引く・構造を保つために必要な列だけです。

| モデル | 平文の列 | 暗号化する中身 |
|---|---|---|
| `StoredClip` | id（内容キー）・コピー時刻・`.data` のパス・サムネイルの有無 | タイトル・種別・カラーコードか否か |
| `StoredClip` のサムネイル | ― | 縮小した PNG（`sealedThumbnail`） |
| `StoredFolder` | id・番号・有効 | フォルダ名 |
| `StoredSnippet` | id・番号・有効・所属フォルダ | タイトル・本文 |

**付加データ（AAD）にモデル名・id・項目名を入れる**ので、暗号文を別の行や別の項目へ差し替えられても復号に失敗して気づけます。

**鍵はキーチェーンに新しく作らず**、`.data` 用の鍵（`clipDataEncryptionKey`）から HKDF-SHA256 で 2 本導出します（salt は `io.github.boyaki-machine.Thoth.store`）。

| 用途 | info |
|---|---|
| 項目の暗号化 | `io.github.boyaki-machine.Thoth.store.seal.v1` |
| 内容キー（HMAC） | `io.github.boyaki-machine.Thoth.store.content-key.v1` |

**履歴の id は、内容から決まるハッシュそのものではなく HMAC-SHA256（内容キー）にします。** 平文の列に置いても、短いパスワードなどを総当たりで照合する手掛かりにならないようにするためです。同じ内容なら同じ id になるので、「同じ内容を上書き」の判定はそのまま行えます。

導出の定数・AAD の形・暗号文の形式は、保存済みのデータを読めるかどうかに直結します。変えるときは移行を用意してください。`FieldCipherSpec` が、Swift の実装とは独立に計算した固定値（HKDF / HMAC は Python の hmac、AES-GCM は Ruby の OpenSSL）で押さえています。

- サムネイルは表示サイズの 2 倍の画素に描き直した PNG です。v1.4.x までは「縮小」できておらず、元の解像度の画像が平文で `~/Library/Caches` に残っていました（v1.5 で作り直して暗号化し、旧キャッシュは削除します）。
- 既存の平文 `.data` は、起動後のバックグラウンド処理で暗号化形式へ移行されます（移行前のファイルも読めるよう後方互換を保持）。
- 鍵は macOS キーチェーンに保存されます（[4. 情報の分類](#4-情報の分類ユーザー設定情報--アプリ生成情報)）。

### 2-4. TOTP

RFC 6238 に準拠します。

| 項目 | 値 |
|---|---|
| アルゴリズム | HMAC-SHA1 / SHA256 / SHA512（otpauth URI の `algorithm` で指定、既定 SHA1） |
| 桁数 | 既定 6（`digits`） |
| 周期 | 既定 30 秒（`period`） |
| 入力形式 | `otpauth://totp/...` URI、または生の Base32 secret |

Base32 デコードは、実在サービスが発行するランダムな secret（末尾ビットが非ゼロになり得る）を受け入れるため、RFC 4648 の末尾ビット厳格検証は行いません（主要な認証アプリと同じ寛容な挙動）。

## 3. 他プラットフォーム互換のための取り決め

将来、他 OS（Windows 等）で本アプリと相互運用するアプリケーションを実装する場合、以下がプラットフォーム非依存の互換ポイントです。逆に、これら以外（SwiftData のストア、`.data` ファイル、キーチェーン）は端末固有であり移植・共有の対象外です。

### 相互運用できるもの

| 対象 | 形式 | 備考 |
|---|---|---|
| **暗号化ファイル**（`.enc`） | 2-1 のコンテナ形式 | 標準プリミティブ（PBKDF2-HMAC-SHA256 + AES-256-CBC + HMAC-SHA256）のみで構成。他言語の標準ライブラリで再実装可能。Mac で暗号化 → 他環境で復号が可能 |
| **セキュア情報の Export/Import** | 1 の `SecureUserData` JSON | 単なる JSON。`version` フィールドで将来の形式変更に対応。ファイル経由で端末間共有が可能 |
| **TOTP** | RFC 6238 + otpauth URI | 完全に標準準拠 |

### 実装時の指針

- 暗号化コンテナを再実装する場合、45 バイトのヘッダーレイアウトと 80 バイト PBKDF2 導出（32+16+32 分割）を厳密に守ること。HMAC は「先頭 13 バイト + 本体全体」を対象とする。
- JSON スキーマを変更する場合は `version` を上げ、旧バージョンを読めるよう寛容にデコードすること（本アプリの既存デコードもこの方針）。
- 相互運用の回帰を防ぐため、両実装で共有できるテストベクタ（固定の暗号文・固定 JSON）を用意することを推奨します。本リポジトリの `CryptoServiceSpec` / `SecureMenuItemSpec` に固定フィクスチャの例があります。

## 4. 情報の分類（ユーザー設定情報 / アプリ生成情報）

本アプリがキーチェーンに保存する情報は、性質に基づいて **2 つのエントリ**に集約されています。この分類が「Export 対象か否か」「端末間で共有できるか否か」の境界と一致します。

| 分類 | キーチェーンエントリ | 内容（JSON スキーマ） | Export | 端末間共有 |
|---|---|---|---|---|
| **ユーザー設定情報** | service: `io.github.boyaki-machine.Thoth.SecureMenu`<br>account: `user-data` | `SecureUserData`<br>`{version, items, cryptoPassword}` | 対象 | 可能 |
| **アプリ生成情報** | service: `io.github.boyaki-machine.Thoth.Database`<br>account: `app-keys` | `AppGeneratedKeys`<br>`{version, realmEncryptionKey, clipDataEncryptionKey}` | 対象外 | 不可（端末固有） |

このほか、コード署名の安定化に使う自己署名証明書（`kSecClassIdentity`、CN: `Thoth Local Signing`）がキーチェーンに保存されます（[DEVELOPMENT_JP.md](DEVELOPMENT_JP.md) の「コード署名」参照）。

### 鍵管理のフェイルセーフ

アプリ生成鍵（DB / `.data` 暗号鍵）の扱いには、データ消失を防ぐための安全策があります。

- キーチェーン読み出しが `errSecItemNotFound` **以外**で失敗した場合、鍵は**新規作成しない**（鍵が存在するのに読めない状況で新しい鍵を作ると、既存の暗号化データを永久に開けなくなるため）。
- 鍵の新規作成は**安定署名（Thoth Local Signing）で動作中の場合のみ**行う（ad-hoc 署名のまま作成すると、再署名後に読めなくなるため）。それ以外では暗号化を保留し、平文のまま起動して次回以降に再試行する。
- 新規作成した鍵は、書き込み後に**読み戻して一致を検証**してから使用する。
- 旧形式（個別エントリ）からの移行は、新エントリへの書き込みと読み戻し検証に成功した場合のみ旧エントリを削除する。

## 5. 性能設計・設計方針

コードを読む前に把握しておくと理解が早い、全体的な設計方針をまとめます。

### 5-1. 起動シーケンス（メニューバー表示までの最短化）

起動処理はフェーズ分割され、メニューバーアイコンの表示を最優先にしています（詳細なシーケンス図は `AppDelegate.swift` のコメントを参照）。

- **軽量な同期処理**（DI・アイコン表示）を先に行い、メニューバーアイコンを即座に表示する。
- **重い初期化**（鍵の取得・ストアを開く・初回は Realm からの移行）はバックグラウンド（`LibraryProvider.prepare`）で行う。完了は `LibraryProvider.isReady` フラグで管理し、完了前にメニュー再構築などが保存層に触れないようガードする。
- **自己再署名**（`codesign --deep` 等、数秒かかる外部コマンド）はバックグラウンドで実行し、失敗時のみ通常起動にフォールバックする。
- **ログイン項目の確認ダイアログ**（modal）はサービス起動完了後に遅延表示する。

### 5-2. クリップボード監視とスレッド

- NSPasteboard には変更通知 API が無いため、`changeCount` を **100ms 間隔でポーリング**して変化を検出します。この常駐処理は `.utility` QoS で動作します（`changeCount` の読み取りは極めて軽量なため、高効率コアで十分。体感遅延の上限はポーリング間隔の 100ms で決まり、コア速度には依存しません）。
- 保存処理（重複判定・サムネイル生成・アーカイブ・ファイル書き込み・保存層への追加）は、専用の直列キュー（`.userInitiated`）にまとめて逃がし、メインスレッドを塞ぎません。
- 保存層（SwiftData）の `ModelContext` はスレッドをまたげないため、保存層が持つ専用の直列キューの中でだけ使います。呼び出し側はどのスレッドからでも呼べ、やり取りするのは値型です。
- ペースト・クリップ読み込みなどユーザーが結果を待つ処理は `.userInitiated`、メニュー表示・構築はメインスレッド（`.userInteractive` 相当）で動作します。

> macOS には特定 CPU コアを指定する API はありません。P コア / E コアの使い分けは QoS クラスを通じて OS スケジューラに委ねる設計です。「待機中は高効率コアで静かに、操作時は高性能コアで機敏に」を意図しています。

### 5-3. メニューの遅延再構築

メニュー（NSMenu）はインスタンスを固定し、内容だけを表示直前に再構築します。履歴・スニペット・設定の変更は**世代カウンター**を進めるだけにとどめ、実際の構築コスト（履歴数に比例）はメニューを開く瞬間まで支払いません。これにより、コピーのたびに全メニューを再構築する処理を排除しています（`MenuManager` 参照）。

### 5-4. クリップボードの秘匿

- セキュアメニューの通常項目・パスワード生成結果は、`org.nspasteboard.ConcealedType` / `TransientType` マーカー付きで書き込み、`ClipService` 側でこのマーカーを含むコピーを履歴保存から除外します。これにより、自身の秘匿コピーと、同規約に対応した他のパスワードマネージャー由来のコピーの両方が履歴に残りません。
- TOTP はクリップボードを一切経由せず、`CGEvent` によるキー入力の直接送出で貼り付けます（OS のコピー履歴にも本アプリの履歴にも残りません）。
- セキュアメニューからの貼り付けは、書き込む前のクリップボードの内容（全アイテム・全型）を `PasteboardSnapshot` に控え、⌘V を送った約 2 秒後（`PasteService.concealedPasteRestoreDelay`）にその内容へ戻します。秘匿値がクリップボードに残り続けて ⌘V でもう一度貼り付けられることを防ぎ、利用者が元々コピーしていた内容も失わせません。戻した内容を新しいコピーとして履歴に取り込まないよう、戻す直前に `ClipService.incrementChangeCount()` を呼びます。
- 自動で貼り付けられない場合（「メニュー項目選択後に "⌘ + V" を入力」がオフ・アクセシビリティ権限なし）と、確認ウィンドウ・パスワード生成の「コピー」は、利用者が自分で貼り付けるので 30 秒後にクリアします。
- いずれも、その間にユーザーが別の内容をコピーしていた場合は、それを消さないよう `changeCount` の変化を確認します。
- パネル（履歴・セキュアアイテム）から選んだ値は、貼り付け先のアプリを前面へ戻してから送ります（`CallerAppActivator`）。貼り付け先はホットキーを押した時点の最前面アプリで、認証ダイアログを挟んでも変わりません。`activate` は非同期なので、前面化を要求してから最低 0.2 秒待ち、さらにそのアプリが最前面かつキーボードフォーカスの持ち主（アクセシビリティの focused application）になったのを確かめてから（最大 1 秒）⌘V・キー入力を送ります。前面化の前に送ると Thoth 自身が受け取り、ビープが鳴るか何も起きません。`NSWorkspace.frontmostApplication` と `NSRunningApplication.isActive` は要求の直後（数 ms）にもう相手を指すため、それだけでは判定に使えません。

### 5-5. コード署名の安定化

前述のとおり、キーチェーン ACL がコード署名に紐付く macOS の仕様に対応するため、`CodeSignService` が起動時にデバイス固有の証明書で自己再署名します。これにより、ローカルビルドを重ねてもセキュアアイテムを読み続けられます（詳細は [DEVELOPMENT_JP.md](DEVELOPMENT_JP.md)）。

### 5-6. セキュア情報確認ウィンドウ

セキュア情報を一覧しながら確認・編集する 2 ペインのウィンドウ（メインメニュー → 「セキュア情報」、または選択パネル末尾の「セキュア情報確認 (&s)」）。設計上の判断は次のとおりです。

**セキュアアイテム管理ウィンドウの廃止（v1.3.0）**

v1.2.x までは、同じ役割の画面が 2 つありました。セキュアアイテム**管理**ウィンドウ（選択パネルの `p` キー、一覧 + 編集シート）と、この**確認**ウィンドウ（メインメニューの `s` キー、2 ペイン）です。v1.2.x で確認ウィンドウを作り込んだ結果、管理ウィンドウは機能的にほぼ完全な部分集合になり、2 画面を並行して保守する理由が無くなりました。

**機能面より先に、セキュリティ面が決め手でした。** 管理ウィンドウには `sharingType = .none`（画面共有・収録からの除外）も表示前の認証ゲートもありません。同じ平文を、片方だけ保護が薄い経路で見られる状態を残すべきではないと判断しました。

移植したもの・しなかったものの判断は次のとおりです。

| 管理ウィンドウにあった機能 | 判断 | 理由 |
|---|---|---|
| パスワード生成への導線 | **移植した**（改善つき） | 唯一の欠落だった。下記参照 |
| 複数選択の一括削除 | 移植しない | 確認ウィンドウは「選択アイテムの詳細を右ペインに出す」構造で複数選択と相性が悪い。⌘Z で戻せるため 1 件ずつで足りる |
| 履歴エントリの個別削除 | 移植しない | 過去の値は認証システムのロールバック時の退避経路。この画面から失う手段を作らない（下記「変更履歴の参照」） |
| 一覧の「フィールド数」列 | 移植しない | 選択したアイテムの詳細が常に右ペインに出るため代替されている |
| 編集シートの Cancel（破棄） | 移植しない | 確認ウィンドウは自動保存 + ⌘Z の設計。破棄という概念を持ち込むと保存モデルが二重になる |

選択パネル末尾の行は、宛先を確認ウィンドウへ移し、キーもメインメニューと揃えて `p` → `s` に変更しました（`p` は解放したまま）。この行の**表示ラベルとキー処理は別ファイルに書かれている**ため、片方だけ直すと「(&s) と出ているのに `s` で開かない」状態になります。`CPYSecurePickerPanelSpec` で両方を突き合わせています。

選択パネルは開く時点で認証済みなので、そこから確認ウィンドウを開いても `SecureMenuService.authenticationGracePeriod`（30 秒）の猶予に入り、Touch ID は再要求されません。

**選択パネル（⌘⇧.）との棲み分け**

選択パネルは「素早く選んで貼る」ための幅 260px・1 行 22px の UI で、長文を載せる場所がありません。メモ（`note`）はこのパネルから除外し、確認ウィンドウ専用としています（**除外するのは表示だけで、検索の対象には含めます**。後述「検索の条件」）。URL は貼り付けたい場面があるため、パネルにも `🔗` 付きで表示します。

サブパネルに載せるフィールドの決定は `CPYSecurePickerPanel.subPanelFields(for:)` の 1 箇所に集約しています。選択確定時に記録される `fieldIndex` はこの配列に対する添字として「続けて貼り付けモード」の復元にも使われるため、表示側と開閉判定のどちらか一方でも `item.fields` を直接使うと、開き直したときに別のフィールドが貼り付けられます。

**検索の条件（v1.3.1）— 確認ウィンドウと選択パネルで共通**

絞り込みは `SecureItemSearch`（UI 非依存）に集約し、**確認ウィンドウの検索窓と選択パネル（⌘⇧.）の検索窓は同じ条件**で動きます。条件を変えるときはこの型だけを直します。

v1.3.0 までは 2 つの画面がそれぞれ別の実装を持ち、条件がずれていました。確認ウィンドウはタイトル・ラベル・メモ本文まで、選択パネルはタイトルとラベルだけ（しかも複数語の AND は「1 つのラベルの中で全語一致」しか通らない）という状態です。同じ語で探しても片方にしか出ないアイテムが生まれ、**「登録したはずのものが見つからない」という誤解に直結する**ため、条件を揃えました。

| 項目 | 扱い |
|---|---|
| タイトル・全フィールドのラベル | 対象 |
| マスク（🔒）が掛かっていないテキスト・URL の値 | 対象。ログイン ID や URL のドメインの断片から「どのアカウントだったか」を探せる |
| メモ本文 | 対象。契約番号から account を引く用途がある |
| **マスクを掛けたフィールドの値** | **対象外** |
| **TOTP secret** | **対象外** |
| 複数語（空白・改行区切り） | AND 条件。語はタイトル・ラベル・値をまたいでよい（"github password" のような探し方） |
| 大文字小文字 | 無視する |

マスク済みの値と TOTP secret を外すのは、値の断片で探す用途が無いうえ、秘密情報を検索窓へ打たせる動機を作らないためです（検索窓に打った文字は伏せ字になりません）。メモはマスクの概念を持たない種別なので、旧データや取り込んだ JSON で `isPassword` が立っていても本文を対象にします。

種別ごとの規則は `SecureMenuItem.Field.Kind.valueSearchability` に集約し、マスク指定との組み合わせは `Field.isValueSearchable` が決めます。`default` の無い switch で書いてあるため、種別を足すと判断が必要な箇所がコンパイルエラーとして表面化します。

**選択パネルに出ないメモも、選択パネルの検索対象に含めます。** 絞り込みの結果として並ぶのは親アイテムだけで、一致した値そのものはどちらの画面にも表示されないため、対象を画面ごとに変える理由がありません。逆に外すと「確認ウィンドウでは出るのにパネルでは出ない」差が戻ります。`SecureItemSearchSpec` の「画面間で条件が揃っていること」が両画面の結果の一致を固定しています。

**右ペインを NSTableView にしていない理由**

- メモの `NSTextView` は行高が可変で、テーブルの自動行高とは相性が悪い
- セル再利用があると「👁 で表示中のパスワードが別のフィールドの行に残る」事故が起きうる。行ビューを使い捨てにすれば、その危険が構造的に無くなる

**保存のタイミング**

キー入力ごとの遅延保存（debounce）は行いません。`SecureMenuService.save(_:)` は値が変わるたびに変更履歴を 1 件積み（上限 10 件）、打鍵の途中経過が履歴を食い潰して本当の旧値が押し出されてしまうためです。確定の契機は「編集終了・選択アイテムの切り替え直前・ウィンドウ非アクティブ化・アプリ終了・⌘S・最後の入力から 20 秒（保険）」に限定しています。

**マスク中は値を編集できない**

伏せ字を表示したまま編集させると、画面に見えている `••••••••` がそのまま値として保存されます。編集するには 👁 で平文に切り替える必要があります。TOTP は secret を表示しないため常に編集不可です。キーチェーンを読み出せない状態（`isKeychainAccessDenied`）では、保存が拒否されるだけで入力内容が失われるため、入力の時点で止めます。

**平文表示の保護**

| 保護 | 内容 |
|---|---|
| 認証ゲート | 表示前に `secureMenuService.authenticate()` を通す（30 秒の猶予は共通） |
| 自動再マスク | 👁 で表示した値は 30 秒で伏せ字へ戻す。ウィンドウ非アクティブ化でも即座に戻す |
| 画面キャプチャ除外 | `NSWindow.sharingType = .none` |
| 画面ロック / スリープ | `com.apple.screenIsLocked`（分散通知）と `NSWorkspace.willSleepNotification` で保存後にクローズ |
| メモリ | クローズ時に保持している平文を破棄し、次に開いたときに読み直す |
| URL を開く | `http` / `https` かつホスト名を持つ場合のみ。インポート由来の `file://` や独自スキームで意図しないアプリが起動するのを防ぐ |

**画面間の同期**

セキュアアイテムを扱う画面は同じ `SecureMenuService` を共有します。変更は `Notification.Name.secureItemsDidChange` で通知し、発火点は `saveAllItems`（保存・削除・並べ替え）と `deleteAllItems` の 2 つです（後者は `saveAllItems` を通らないため、片方だけでは全削除が同期されません）。

v1.3.0 で管理ウィンドウを廃止したあとも、この仕組みは残します。確認ウィンドウを開いたままアプリを再アクティブ化して選択パネルを使う経路があり、また新しい画面を足したときに同期の土台が要るためです。

確認ウィンドウは `SecureMenuService.itemsChangeToken` で「自分が起こした変更か」を判定します。自分の保存で読み直すと行ビューが作り直され、入力中のフォーカスとカーソル位置が飛ぶためです。未保存の編集がある場合は勝手に読み直さず、案内バーを出して読み直すかどうかをユーザーに委ねます。

**取り消し（⌘Z）— 2 層の構成**

v1.2.1 で追加しました。取り消しは 2 つの層に分かれています。

| 層 | 担当 | 範囲 | 寿命 |
|---|---|---|---|
| 入力中 | AppKit 標準（フィールドエディタ / `NSTextView`） | 打鍵単位 | フォーカスが外れるまで |
| 確定後 | `SecureInfoUndoStack` | 保存 1 回分 | ウィンドウを閉じるまで |

アプリ側が扱う単位は **「Keychain へ 1 回書き込むごと」** です。これは既存の保存設計（打鍵ごとの遅延保存を行わず、確定は編集の区切りだけ）をそのまま粒度として使ったものです。入力中の ⌘Z は `keyAction(...)` が `nil` を返して素通しし、標準の打鍵 Undo に譲ります。

控えを積むのは Keychain を書き換える 5 経路のみです。編集系（タイトル・ラベル・値・マスク指定・フィールドの追加削除並べ替え）はすべて `save(_:)` を通るため、そこ 1 箇所で足ります。残りはアイテムの追加・削除・並べ替えとインポートです。

**書き戻しには `save(_:)` ではなく `reorderItems(_:)` を使います。** `save(_:)` は値が変わるたびに変更履歴を 1 件積むため（上限 10 件）、取り消しのたびに履歴が消費され、本当の旧値が押し出されてしまいます。`reorderItems(_:)` は渡した配列をそのまま書き戻すので履歴を汚しません。

**スタックは削除・編集前の平文を保持します。** 破棄する場所は 3 つで、どれか一つでも漏らすとメモリに機微情報が残るか、他のウィンドウの変更を巻き戻します。

| 破棄する場面 | 理由 |
|---|---|
| ウィンドウを閉じるとき | 閉じたあとに平文を残さない（`clearSensitiveData()` と対で呼ぶ） |
| データを読み直すとき | 控えが現在のデータと食い違う |
| 他の画面の変更で案内バーを出すとき | 読み直さない経路。残すと取り消した瞬間に相手の変更ごと巻き戻る |

**削除は確認ダイアログではなく「隠す + 戻せる」で守る**

v1.2.0 ではフィールド削除に確認ダイアログを出していましたが、毎回出るため惰性で通してしまい、通したあとに取り返す手段がありませんでした。コピー ⧉ と削除 🗑 が 2pt 間隔で隣り合っていたことが誤爆の直接の原因です。

v1.2.1 では確認ダイアログを廃止し、🗑 を**ボタンスタックの外**に出して 10pt の余白で分離したうえ、マウスが行に乗っているとき（またはその行を編集中のとき）だけ表示します。スタックに入れたまま `isHidden` にすると幅が畳まれて他のボタンが横滑りし、狙って押せなくなるため、構造として分けています。発見性の補いとして行の右クリックメニューにも削除を置いています。

**アイテムの削除には確認を残しています。** フィールド単位より影響が大きく、削除後は選択が外れて「何が消えたか」が画面から見えなくなるためです。

**並べ替えのドラッグ&ドロップ**

左ペイン（アイテム）は `NSTableView` 標準の仕組みです。**絞り込み中はドラッグを拒否します**。見えている順と保存順が一致せず、行番号から移動先を決められないためです（キー操作の並べ替えも同じ理由で止めています）。

右ペイン（フィールド）は `NSStackView` なので自前実装です。行の左端に掴み手 `≡` を置き、**そこからしかドラッグを始めません**。行全体を掴めるようにすると、値欄のテキスト選択ドラッグと衝突します。掴み手の `NSImageView` は `NSControl` の一員で `mouseDown` を自分で握ってしまうため、`hitTest` でその範囲だけ行へ回しています。

ペイストボードに載せるのは `fieldID` と行番号だけで、**値は決して載せません**。ドラッグ中のペイストボードは他のアプリからも読めるためです。あわせて `draggingSession(_:sourceOperationMaskFor:)` で `.withinApplication` 以外を拒否し、行をアプリの外へ引き出せないようにしています。

**ドラッグ中に出す絵は行の写しにしません。** ドラッグの絵は行を離れてシステム側のウィンドウに描かれるため、このウィンドウに掛けた `NSWindow.sharingType = .none`（画面共有・収録からの除外）が効きません。行を丸ごと写すと、👁 で表示中のパスワードやメモの本文が画面収録に入りえます。**ラベルだけ**を描けば、選択パネルにも出ている情報しか外へ出ず、どのフィールドを掴んでいるかも分かります（値は検索の対象にはなりますが、どちらの画面にも表示されないため根拠にはできません）。外へ出る情報は `SecureFieldRowView.makeDraggingItem()` の 1 箇所だけで決まります。

**入出力（インポート / エクスポート）**

処理は `SecureItemsTransfer`（UI 非依存）に集約しています。左ペイン下部の ⚙ メニューから呼び出します。

**読み出せない状態（`isKeychainAccessDenied`）ではどちらも実行しません。** 取り込みは `saveAllItems` に拒否されるだけですが、書き出しは 0 件の JSON を作ってしまい、ユーザーが既存のバックアップを空で上書きする事故につながります。

この確認は **`SecureItemsTransfer.exportData(using:)` の中**で行います。呼び出し側の入口判定（⚙ メニューの有効・無効、`allowsTransfer`）が見ているのは直近の読み込み結果を写した控えなので、保存パネルを開いている間に読めなくなった場合を取りこぼします。実際に書き出す直前に読み直して確かめる必要があります。

インポートはこの機能のなかで最も取り返しがつかないため、取り込み後も取り消しが効く状態にします（`reloadItems(clearsUndoHistory: false)`）。

**ただし取り消しが戻すのはアイテムだけで、指紋パスワードは戻りません。** 指紋パスワードの置き換えは「現在のパスワードで暗号化したファイルが開けなくなる」旨の確認を通したときにしか起きないため、取り消しが部分的になることを承知で許容しています。

**変更履歴の参照（v1.2.2）**

編集シートと同じ変更履歴（`Field.history`、上限 10 件）を確認ウィンドウからも見られるようにしました。用途は 2 つで、どちらも「値が見えること」を要求します。

1. 認証システムに「過去 N 回と同じパスワードは不可」という制約があるため、新しいパスワードを決める前に過去の値を**目視で見比べる**
2. 認証システムのロールバックで巻き戻ったとき、過去のパスワードが**退避経路**になる

**メニューではなく行の下にインラインで展開します。** 値が画面に出る以上、置き場は保護の効く場所でなければなりません。`NSWindow.sharingType = .none`（画面共有・収録からの除外）が効くのはウィンドウの中だけで、NSMenu や NSPopover は別ウィンドウに描かれるため守られません（ドラッグ画像と同じ論点）。廃止した編集シートはメニューに平文を並べていましたが、確認ウィンドウは「平文を守る」ことを前提にしているため、同じ作りにはしていません。

履歴には行と同じ規律をそのまま通します: 既定はマスク / 👁 で平文・`revealTimeout` 秒で自動再マスク / ウィンドウ非アクティブ化で即伏せ字 / コピーは秘匿マーカー付きで自動クリア。失効時間は `SecureFieldRowView.revealTimeout` を共有し、「画面に残り続ける時間の上限」を 1 箇所で決めています。`startRefreshTimerIfNeeded()` の起動条件に履歴側の平文表示を含めていないと、履歴だけを開いたときに自動再マスクが働きません。

🕘 は**履歴が 1 件以上ある行**で、マウスが乗っているか編集中のときだけ出します。削除ボタンと違いスタックの中ほどに入るため、出し入れは `isHidden` ではなく `alphaValue` で行います（幅を確保したままにして、現れた瞬間にコピー ⧉ が横へ動かないようにするため）。履歴を残さない種別（TOTP / メモ）では出しません。TOTP の secret は「極めて機微なため履歴を残さない」設計なので、旧データに残っていたとしても見せません。

**確認ウィンドウの履歴は読み取り専用です。** 削除も「この値に戻す」も設けていません。上記 2 の用途があるため、この画面から履歴を失う手段を作らない判断です。値を戻したいときは現在値を書き換えれば、その操作で現在値が自動的に履歴へ入ります。閲覧は破壊的でないため、読み取り専用モードでも使えます。

**パスワード生成（v1.3.0）**

廃止した管理ウィンドウの編集シートから引き継いだ導線です。ボトムバーの「パスワード生成...」（**⌘G**）で既存の生成画面をシートとして開きます。

**生成値を直接フィールドへ入れる導線は設けていません。** 生成した値は「コピー」でクリップボードへ取り、貼り付けてもらいます。実装としては一度試しており、次の順で行き詰まりました。

1. 最初は「直前にフォーカスが入っていたフィールド」へ入れる作りにした。**マスク中の値欄は編集不可**（`isValueEditable`）でフォーカスが入らないため、記録はほぼ常に空。ラベルを選んだ人にしか効かなかった
2. 代わりに「マスク指定がちょうど 1 つならそこへ」で補った。text + password の持ち物では常に password 欄が選ばれ、利用者が見ている text 欄には入らない。**マスク欄は空でも `••••••••`** と表示されるため取り違えにも気づけず、password 欄が 2 つある持ち物では候補を絞れず導線ごと消えた
3. シート上に「入力先」ポップアップを置いて選ばせる形にした。取り違えは解けたが、**生成画面としては操作が重い**

生成画面を開く頻度は高くないため、コピー＆ペーストの手数は許容できると判断しました。**「どこへ入るか」を画面の外で決めない**のが、この判断の核です。

**エクスポート／インポートでの履歴の扱い（v1.2.2 時点の調査結果）**

| 経路 | 挙動 |
|---|---|
| エクスポート | 履歴も**含まれる**（過去のパスワードが平文で JSON に載る） |
| インポート | 履歴も**読み込まれる** |
| 既存アイテムへの再インポート | 現在の履歴が**ファイルの履歴で置き換わる**（値が変わっていれば旧値が 1 件追記される） |

3 番目は `mergeFieldHistories` が取り込む側の `field.history` を基点にしているためで、「ポップアップから履歴を削除したら保存に反映する」ための意図的な設計です。インポート経路では「古いバックアップを取り込むと履歴が巻き戻る」という副作用になります。

**⚙ メニューに取り消しを置く理由**

削除ボタンがホバーでしか出ないぶん、「戻せる」ことは目に見えている必要があります。項目名には `undoAction` から組み立てた操作名（「"削除" を取り消す」など）を出し、何が戻るのかを示します。

### 5-7. Realm から SwiftData への移行（v1.5）

保存先を Realm から SwiftData へ移しました。移行は **v1.5.x を初めて起動したときに 1 回だけ**行います。

1. Realm を**読み取り専用**で開き、全件を値型（`ClipRecord` / `SnippetFolderRecord` / `SnippetRecord`）に読み出す
2. 本番の場所（`Thoth.store`）に新しいストアを作り、暗号化して書き込む（履歴の id は内容キーに置き換える）
3. **新しい `ModelContext` で読み直し**、件数・全項目・並び順を照合する
4. 照合に通ったときだけ、隣に**完了の印**（`Thoth.store.ready`）を書く

- **Realm のファイルには一切書き込みません。** v1.6.x まで残すので、v1.4.x に戻せば移行した時点のデータが見えます（移行後に v1.5.x で行った変更は旧版には見えず、旧版で行った変更も v1.5.x には反映されません。既知の制限）。
- **完了の印が無いストアは、移行が途中で止まったもの**です。アプリは印のあるストアしか使わないため、利用者のデータは入っていません。次の起動時に、開く前に消してやり直します。
- 印があるのに開けないストアは、削除せず `Thoth.store.broken-<日時>` へ退避します。
- 一時ファイルに書いてから移す方式は採っていません。SwiftData にはストアを閉じる手段が無く、開いたことのあるファイルを動かすと SQLite が壊れる（`SQLITE_IOERR_VNODE`）ためです。
- サムネイルは旧キャッシュ（平文・元の解像度）から移さず、`.data` から作り直します。そのうえで旧キャッシュのフォルダを削除します。

**暗号鍵が使えないときは、その起動中はディスクに何も書きません。** 次の 3 つの状態が該当します。

| 状態 | 起きる例 |
|---|---|
| 鍵はあるが読めない | ログインキーチェーンがロックされている、アクセス確認で拒否した、署名が変わって許可の設定と合わない |
| 鍵がまだ無く、作れない | 自動の再署名に失敗して ad-hoc 署名のまま動いている |
| 鍵は読めたが合わない | キーチェーンがリセットされて別の鍵が作られた |

- 履歴はメモリ上だけで記録します（その起動中は貼り付けに使えます）。
- **スニペットは表示も編集もしません。** 一覧が空に見える状態で編集させると、作ったものが終了時に黙って消え、復旧後に二重にもなるためです。メニューは理由を示す 1 行だけにし、編集ウィンドウは編集を拒否してシートで理由を示します（セキュア情報の `isKeychainAccessDenied` と同じ流儀）。
- ストアの削除も、新しい鍵での上書きもしません。原因が解消すれば、次の起動で元どおり読めます。
- セキュア情報（パスワード・TOTP）はキーチェーンの別のエントリにあり、この鍵を使わないため影響を受けません。
