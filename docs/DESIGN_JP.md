## 1. Export / Import されるファイルのスキーマ

セキュアアイテム管理ウィンドウの Export で書き出される JSON は、**ユーザー自身が設定した機微情報**（`SecureUserData`）です。Import はこのファイルを読み込みます。アプリが自動生成する環境固有の情報（暗号鍵など）は Export に含まれません（[4. 情報の分類](#4-情報の分類ユーザー設定情報--アプリ生成情報) を参照）。

> **注意:** Export ファイルは平文の JSON です。取り扱いに注意してください。

### `SecureUserData`（Export/Import のルート）

| キー | 型 | 説明 |
|---|---|---|
| `version` | Int | スキーマバージョン（現行 `2`） |
| `items` | `SecureMenuItem[]` | セキュアアイテムの配列 |
| `cryptoPassword` | String?（省略可） | ファイル暗号化の固定パスワード（指紋パスワード）。未登録なら省略 |

### `SecureMenuItem`

| キー | 型 | 説明 |
|---|---|---|
| `itemID` | String | アイテムの安定 ID（UUID） |
| `title` | String | 表示名（例: "GitHub"） |
| `fields` | `Field[]` | フィールドの配列 |
| `displayOrder` | Int | メニューでの表示順 |

### `SecureMenuItem.Field`

| キー | 型 | 説明 |
|---|---|---|
| `fieldID` | String | フィールドの安定 ID（UUID）。ラベル変更後も履歴を追従させるために使用 |
| `label` | String | フィールド名（例: "Password"） |
| `value` | String | 値。TOTP の場合は otpauth URI / Base32 secret |
| `isPassword` | Bool | 値をマスク表示するか |
| `kind` | String | `"plain"` または `"totp"`（後述の後方互換のため、この 2 値しか書き込まれません） |
| `contentKind` | String（省略可） | 拡張種別 `"url"` / `"note"`。v1.2.0 で追加。通常の種別では出力されません |
| `history` | `FieldHistoryEntry[]` | 値の変更履歴（`plain` / `url` のみ記録。`totp` / `note` は残しません） |
| `createdAt` | Date | 作成日時 |

#### フィールド種別

| 種別 | JSON 表現 | 用途 |
|---|---|---|
| `plain` | `kind: "plain"` | ID・パスワードなど通常のテキスト |
| `totp` | `kind: "totp"` | `value` に otpauth URI / Base32 secret を保持し、選択時にワンタイムコードを生成 |
| `url` | `kind: "plain"` + `contentKind: "url"` | ログイン先などの URL。ブラウザで開ける |
| `note` | `kind: "plain"` + `contentKind: "note"` | 契約番号・連絡先などの複数行メモ |

### `FieldHistoryEntry`

| キー | 型 | 説明 |
|---|---|---|
| `value` | String | 過去の値 |
| `replacedAt` | Date | 置き換えられた日時 |

### 後方互換

- デコードは寛容に行われ、欠けているキーはデフォルト値で補完されます（`version` 欠落時は現行版、`kind` 欠落時は `plain`、`history` 欠落時は空、など）。
- **未知の種別は `plain` にフォールバックします。** 将来のバージョンが書いた種別を古いバイナリが読んでも、デコード自体は成功し値は保持されます。
- Import は現行形式（`SecureUserData` オブジェクト）を優先し、**旧形式（`SecureMenuItem` の配列のみ）の JSON もフォールバックで読み込めます**。過去バージョンで書き出したファイルもそのまま取り込めます。

### 前方互換（バージョンを戻した場合）

拡張種別（`url` / `note`）を `kind` キーに直接書くと、v1.1.x 以前は `kind` を enum として厳密にデコードするため **例外が発生し、セキュアアイテム全体が読めなくなります**。読めないデータの上に保存すると全件が失われるため、拡張種別は新しいキー `contentKind` に分離しています。

- 旧バージョンは `contentKind` を未知のキーとして無視し、`kind: "plain"` として読みます。
- **値は失われません。** TOTP secret も `kind: "totp"` のまま維持されます。
- ただし旧バージョンで保存し直すと `contentKind` が失われ、URL / メモは通常のテキストに降格します（値は残ります）。またメモを旧バージョンの単一行フィールドで編集すると改行が失われます。

### 読み出し不能時の保護

「Keychain の読み出しには成功したが内容を解釈できない」場合（データ破損など）、`SecureMenuService` は `errSecDecode` を返して読み出し不能として扱い、**すべての書き込みを拒否します**。空のデータで既存データを上書きしないための保護です。旧エントリからの移行も、旧データを解釈できない場合は移行を中止して旧エントリを残します。

## 2. 暗号化 / 復号に関する仕様

### 2-1. ファイル暗号化コンテナ（現行: バージョン 2）

**設計要件:** 「アプリが無い端末でも `openssl` コマンドだけで復号できること」。このため、暗号化本体を `openssl enc` の出力と完全互換にし、その外側に HMAC-SHA256 による認証（Encrypt-then-MAC）を付与しています。

**バイトレイアウト:**

| オフセット | サイズ | 内容 |
|---|---|---|
| 0 | 7 | マジック `"CLPYENC"`（ASCII） |
| 7 | 1 | バージョン `0x02` |
| 8 | 1 | フラグ（bit0: フォルダ由来 → 復号後に tar 展開） |
| 9 | 4 | PBKDF2 反復回数（UInt32 ビッグエンディアン、既定 200000） |
| 13 | 32 | HMAC-SHA256 タグ（先頭 13 バイト + 本体全体を認証） |
| 45 | 可変 | 本体 = `openssl enc` 完全互換:<br>`"Salted__"(8B) + salt(8B) + AES-256-CBC 暗号文（PKCS7 パディング）` |

**鍵導出:** PBKDF2-HMAC-SHA256 で **80 バイト**を一度に導出し、以下に分割します。

- 暗号鍵: 先頭 32 バイト
- IV: 続く 16 バイト
- HMAC 鍵: 続く 32 バイト

先頭 48 バイト（暗号鍵 + IV）は `openssl enc -pbkdf2` の鍵導出結果と一致します（PBKDF2 の出力はブロック単位で独立しており、長く導出しても前半は変わらないため）。これが openssl 互換の根拠です。

**認証:** ヘッダー（先頭 13 バイト）と本体全体を HMAC-SHA256 で認証します。アプリ内での復号は、この HMAC タグを**復号前に検証**することで改竄・誤パスワードを確実に検知します。openssl CLI での復号ではこの検証は行われません（誤パスワードの大半は CBC の PKCS7 パディングエラーで検出されます）。

**openssl での復号:**

```sh
# 先頭 45 バイトのヘッダーを取り除いてから openssl enc に渡す
tail -c +46 file.enc | openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -pass pass:PASSWORD -out restored
# フォルダ由来（オフセット 8 のフラグ bit0 が 1）の場合は tar -xf restored で展開
```

### 2-2. 復号のみ対応する過去形式

アプリの復号処理は、以下の過去形式も自動判別して読み込めます（暗号化時の出力は常に現行のバージョン 2）。

| 形式 | 判別 | 仕様 |
|---|---|---|
| バージョン 1 | `"CLPYENC" + 0x01` | AES-256-GCM 形式（旧実装、短期間のみ使用）。ヘッダー 29B + nonce 12B + 暗号文 + タグ 16B |
| レガシー | 先頭がマジックでない | `マーカー 8B + openssl enc 出力`。マーカーは `"CLIPYDIR"`（フォルダ）またはゼロ 8 バイト（ファイル）。鍵導出は PBKDF2-HMAC-SHA256 100000 回 |

`openssl enc -aes-256-cbc -pbkdf2` が出力した標準ファイル（マーカーなし）も、レガシー形式のファイル版として復号できます。

### 2-3. クリップボード履歴の暗号化（保存時暗号化）

クリップボード履歴は、Realm データベースと個別の `.data` ファイル（クリップ実データ）の2箇所に保存され、いずれも暗号化されます。これらはアプリ内部専用の鍵で暗号化され、**端末固有**です（Export 対象外・他端末とは互換しません）。

| 対象 | 方式 |
|---|---|
| Realm データベース | Realm 標準の暗号化（AES-256、64 バイト鍵） |
| クリップ `.data` ファイル | AES-256-GCM。形式: `"CLPYDAT"(7B) + バージョン 0x01(1B) + AES-GCM combined（nonce 12B + 暗号文 + タグ 16B）` |

- 既存の平文データベース・平文 `.data` は、初回起動時・起動後のバックグラウンド処理で暗号化形式へ移行されます（移行前のファイルも読めるよう後方互換を保持）。
- 鍵は macOS キーチェーンに保存されます（[4. 情報の分類](#4-情報の分類ユーザー設定情報--アプリ生成情報)）。

### 2-4. TOTP

RFC 6238 に準拠します。

| 項目 | 値 |
|---|---|
| アルゴリズム | HMAC-SHA1 / SHA256 / SHA512（otpauth URI の `algorithm` で指定、既定 SHA1） |
| 桁数 | 既定 6（`digits`） |
| 周期 | 既定 30 秒（`period`） |
| 入力形式 | `otpauth://totp/...` URI、または生の Base32 secret |

Base32 デコードは、実在サービスが発行するランダムな secret（末尾ビットが非ゼロになり得る）を受け入れるため、RFC 4648 の末尾ビット厳格検証は行いません（主要な認証アプリと同じ寛容な挙動）。

## 3. 他プラットフォーム互換のための取り決め

将来、他 OS（Windows 等）で本アプリと相互運用するアプリケーションを実装する場合、以下がプラットフォーム非依存の互換ポイントです。逆に、これら以外（Realm DB、`.data` ファイル、キーチェーン）は端末固有であり移植・共有の対象外です。

### 相互運用できるもの

| 対象 | 形式 | 備考 |
|---|---|---|
| **暗号化ファイル**（`.enc`） | 2-1 のコンテナ形式 | 標準プリミティブ（PBKDF2-HMAC-SHA256 + AES-256-CBC + HMAC-SHA256）のみで構成。他言語の標準ライブラリで再実装可能。Mac で暗号化 → 他環境で復号が可能 |
| **セキュア情報の Export/Import** | 1 の `SecureUserData` JSON | 単なる JSON。`version` フィールドで将来の形式変更に対応。ファイル経由で端末間共有が可能 |
| **TOTP** | RFC 6238 + otpauth URI | 完全に標準準拠 |

### 実装時の指針

- 暗号化コンテナを再実装する場合、45 バイトのヘッダーレイアウトと 80 バイト PBKDF2 導出（32+16+32 分割）を厳密に守ること。HMAC は「先頭 13 バイト + 本体全体」を対象とする。
- JSON スキーマを変更する場合は `version` を上げ、旧バージョンを読めるよう寛容にデコードすること（本アプリの既存デコードもこの方針）。
- 相互運用の回帰を防ぐため、両実装で共有できるテストベクタ（固定の暗号文・固定 JSON）を用意することを推奨します。本リポジトリの `CryptoServiceSpec` / `SecureMenuItemSpec` に固定フィクスチャの例があります。

## 4. 情報の分類（ユーザー設定情報 / アプリ生成情報）

本アプリがキーチェーンに保存する情報は、性質に基づいて **2 つのエントリ**に集約されています。この分類が「Export 対象か否か」「端末間で共有できるか否か」の境界と一致します。

| 分類 | キーチェーンエントリ | 内容（JSON スキーマ） | Export | 端末間共有 |
|---|---|---|---|---|
| **ユーザー設定情報** | service: `io.github.boyaki-machine.Thoth.SecureMenu`<br>account: `user-data` | `SecureUserData`<br>`{version, items, cryptoPassword}` | 対象 | 可能 |
| **アプリ生成情報** | service: `io.github.boyaki-machine.Thoth.Database`<br>account: `app-keys` | `AppGeneratedKeys`<br>`{version, realmEncryptionKey, clipDataEncryptionKey}` | 対象外 | 不可（端末固有） |

このほか、コード署名の安定化に使う自己署名証明書（`kSecClassIdentity`、CN: `Thoth Local Signing`）がキーチェーンに保存されます（[DEVELOPMENT_JP.md](DEVELOPMENT_JP.md) の「コード署名」参照）。

### 鍵管理のフェイルセーフ

アプリ生成鍵（DB / `.data` 暗号鍵）の扱いには、データ消失を防ぐための安全策があります。

- キーチェーン読み出しが `errSecItemNotFound` **以外**で失敗した場合、鍵は**新規作成しない**（鍵が存在するのに読めない状況で新しい鍵を作ると、既存の暗号化データを永久に開けなくなるため）。
- 鍵の新規作成は**安定署名（Thoth Local Signing）で動作中の場合のみ**行う（ad-hoc 署名のまま作成すると、再署名後に読めなくなるため）。それ以外では暗号化を保留し、平文のまま起動して次回以降に再試行する。
- 新規作成した鍵は、書き込み後に**読み戻して一致を検証**してから使用する。
- 旧形式（個別エントリ）からの移行は、新エントリへの書き込みと読み戻し検証に成功した場合のみ旧エントリを削除する。

## 5. 性能設計・設計方針

コードを読む前に把握しておくと理解が早い、全体的な設計方針をまとめます。

### 5-1. 起動シーケンス（メニューバー表示までの最短化）

起動処理はフェーズ分割され、メニューバーアイコンの表示を最優先にしています（詳細なシーケンス図は `AppDelegate.swift` のコメントを参照）。

- **軽量な同期処理**（Realm 構成・DI・アイコン表示）を先に行い、メニューバーアイコンを即座に表示する。
- **重い初期化**（スキーマ移行・暗号化移行・初回オープン）はバックグラウンド（`RealmProvider.warmUp`）で行う。完了は `RealmProvider.isReady` フラグで管理し、完了前にメニュー再構築などが移行中の Realm に触れないようガードする。
- **自己再署名**（`codesign --deep` 等、数秒かかる外部コマンド）はバックグラウンドで実行し、失敗時のみ通常起動にフォールバックする。
- **ログイン項目の確認ダイアログ**（modal）はサービス起動完了後に遅延表示する。

### 5-2. クリップボード監視とスレッド

- NSPasteboard には変更通知 API が無いため、`changeCount` を **100ms 間隔でポーリング**して変化を検出します。この常駐処理は `.utility` QoS で動作します（`changeCount` の読み取りは極めて軽量なため、高効率コアで十分。体感遅延の上限はポーリング間隔の 100ms で決まり、コア速度には依存しません）。
- 保存処理（重複判定・サムネイル生成・アーカイブ・ファイル書き込み・Realm 追加）は、専用の直列キュー（`.userInitiated`）にまとめて逃がし、メインスレッドを塞ぎません。
- ペースト・クリップ読み込みなどユーザーが結果を待つ処理は `.userInitiated`、メニュー表示・構築はメインスレッド（`.userInteractive` 相当）で動作します。

> macOS には特定 CPU コアを指定する API はありません。P コア / E コアの使い分けは QoS クラスを通じて OS スケジューラに委ねる設計です。「待機中は高効率コアで静かに、操作時は高性能コアで機敏に」を意図しています。

### 5-3. メニューの遅延再構築

メニュー（NSMenu）はインスタンスを固定し、内容だけを表示直前に再構築します。履歴・スニペット・設定の変更は**世代カウンター**を進めるだけにとどめ、実際の構築コスト（履歴数に比例）はメニューを開く瞬間まで支払いません。これにより、コピーのたびに全メニューを再構築する処理を排除しています（`MenuManager` 参照）。

### 5-4. クリップボードの秘匿

- セキュアメニューの通常項目・パスワード生成結果は、`org.nspasteboard.ConcealedType` / `TransientType` マーカー付きで書き込み、`ClipService` 側でこのマーカーを含むコピーを履歴保存から除外します。これにより、自身の秘匿コピーと、同規約に対応した他のパスワードマネージャー由来のコピーの両方が履歴に残りません。
- TOTP はクリップボードを一切経由せず、`CGEvent` によるキー入力の直接送出で貼り付けます（OS のコピー履歴にも本アプリの履歴にも残りません）。
- 秘匿コピーは、貼り付け後の一定時間経過でクリップボードを自動クリアします（その間にユーザーが別の内容をコピーしていた場合は、それを消さないよう `changeCount` の変化を確認します）。

### 5-5. コード署名の安定化

前述のとおり、キーチェーン ACL がコード署名に紐付く macOS の仕様に対応するため、`CodeSignService` が起動時にデバイス固有の証明書で自己再署名します。これにより、ローカルビルドを重ねてもセキュアアイテムを読み続けられます（詳細は [DEVELOPMENT_JP.md](DEVELOPMENT_JP.md)）。
